2. Concepts you must be able to explain

What is AJAX?

AJAX = Asynchronous JavaScript And XML. The name is historical; in practice it just means: JavaScript makes an HTTP request in the background and updates part of the page with the answer, without reloading the whole page. The browser's normal behaviour when you submit a form is to throw the current page away and load a fresh one from the server. AJAX deliberately prevents that and does the request itself.

Here it's done with jQuery's $.ajax() — a thin wrapper over the browser's XMLHttpRequest. The server answers with JSON (not a full HTML page), and the JavaScript drops that fragment into the page.

What is a WebSocket, and how is it different from AJAX?

AJAX (ex00)WebSocket (ex01–04)
ShapeOne request → one response, then it's overOne connection stays open, both sides send anytime
Who can start a messageOnly the browser asks; server only repliesBrowser and server can push (server can announce "bob joined")
Good forLogin, form submitsLive chat, where others' messages must arrive on their own
URL schemehttp://ws:// (or wss:// over HTTPS)

A chat can't be built on AJAX alone: the browser would have to keep asking "any new messages?" (polling). A WebSocket lets the server push a new message the instant it's posted. That's why the subject requires WebSockets and forbids AJAX for the chat.

What is jQuery, and why is it "the only library"?

jQuery is a JavaScript helper library (the $(...) you see everywhere). The subject allows only jQuery as a front-end library. We load exactly one library file, static/js/jquery.min.js (v3.7.1). The chat's WebSocket is a built-in browser feature (new WebSocket(...)), not a library — so using it does not break the rule. No Bootstrap, no Socket.IO, no React.

What is the CSRF token?

Django blocks POST requests that don't carry a secret CSRF token, to stop other websites from submitting forms as you. Every form includes {% csrf_token %}, and jQuery's $form.serialize() sends that hidden field along with the AJAX POST — which is why login and logout are accepted. (For the WebSocket, Django's session cookie is what authenticates the user.)

Why ASGI / Channels / daphne?

Plain Django speaks WSGI — HTTP request/response only, no long-lived connections. WebSockets need ASGI (asynchronous). We add django-channels (the WebSocket framework) and daphne (an ASGI server). daphne is listed first in INSTALLED_APPS so that runserver becomes an ASGI server able to serve both the normal pages and the WebSocket. The split is wired in d09/asgi.py: HTTP → Django, WebSocket → the chat consumer.

3. How to prove each rule in the browser

Open the developer tools with F12 (or Ctrl+Shift+I) and use the Network tab. This is how you show the evaluator the rules are actually respected.

"Login/logout communicate only through AJAX" & "the page is never refreshed"

  1. Open /account, then DevTools → Network. Tick the Fetch/XHR filter.
  2. Log in. You see one request: POST /account/login, Type = xhr/fetch, and its response is JSON ({"authenticated": true, "html": "…"}). That is the AJAX call.
  3. Switch the filter to Doc (top-level documents). The count stays at 1 — the first page load — and does not increase when you log in or out. No new document = no refresh.
  4. Extra proof the page object survives: in the Console type window.marker = 42 before logging in, then read window.marker after. It's still 42 — a real refresh would have wiped it.
  5. Log out: one more POST /account/logout xhr, still zero new document loads.

"Chat uses jQuery + WebSockets, no AJAX"

  1. Open a chatroom, DevTools → Network → WS filter. You see one entry: ws/chat/general/ with status 101 Switching Protocols (the WebSocket handshake).
  2. Click it → Messages tab: you watch frames flow both ways (your posts going out, others' messages and the user-list coming in).
  3. Switch to the Fetch/XHR filter and chat some more: zero XHR/fetch requests appear. All traffic is on the socket. That's "WebSockets, no AJAX".

"jQuery is the only library"

Network → JS filter. Only three scripts ever load: jquery.min.js (the one allowed library) plus our own account.js / chat.js. No other library is fetched.

5. Exercise 00 — "AJAX my formula!" (app: account)

A login/logout system that talks to the server only through AJAX, on a single page at /account that is never refreshed.

The moving parts

FileRole
account/urls.pyThe 3 URLs: /account (page), /account/login, /account/logout.
account/views.pyThe server logic. login/logout are POST-only and return JSON.
account/templates/account/account.htmlThe page shell with the #account-state box that gets swapped.
…/_logged_out.html / _logged_in.htmlThe two states, as fragments the AJAX responses reuse.
account/static/account/js/account.jsThe AJAX itself.

How "only through AJAX" is achieved

The form's normal submission (which reloads the page) is cancelled with event.preventDefault(), then jQuery sends the request itself:

// account/static/account/js/account.js
$(document).on("submit", "#login-form", function (event) {
    event.preventDefault();                 // stop the browser reloading the page
    var $form = $(this);
    $.ajax({
        type: "POST",
        url:  $form.attr("action"),
        data: $form.serialize(),            // includes the CSRF token
        dataType: "json"
    }).done(function (response) {
        $("#account-state").html(response.html);   // swap in the new state, no reload
    });
});

The handlers are bound to document, not to the form, because the form is removed from the page on every state change — a handler bound to the form itself would die with it.

The server never returns a full page for these two URLs — it returns JSON, the tell-tale sign of an AJAX endpoint:

# account/views.py
@require_POST                                    # GET is refused (405) — POST only
def login(request):
    form = AuthenticationForm(request, data=request.POST)
    if not form.is_valid():
        return JsonResponse({"authenticated": False,
                             "html": _logged_out_html(request, form)})  # form + errors
    auth_login(request, form.get_user())
    return JsonResponse({"authenticated": True,
                         "html": _logged_in_html(request)})             # "Logged as "

6. Exercise 01 — Basic chat (app: chat)

A page with 3 links to 3 chatrooms whose names live in the database; each room is a working chat over WebSockets, for logged-in users only.

chat/routing.pyThe WebSocket URL ws/chat/<slug>/.

Names live in the database (E01.2/3)

Room is a model; the three rooms are inserted by a data migration rather than hardcoded, and the index lists whatever is in the table:

# chat/views.py
@login_required
def rooms(request):
    return render(request, "chat/rooms.html", {"rooms": Room.objects.all()})

Logged-in users only (E01.6)

Two layers: the pages use @login_required; the socket checks the user and refuses anonymous connections. Django's session cookie identifies the user on the socket, thanks to AuthMiddlewareStack in d09/asgi.py.

# chat/consumers.py — connect()
user = self.scope.get("user")
if user is None or not user.is_authenticated:
    await self.close(code=4401)      # anonymous → socket refused
    return

Post a message, everyone in the room sees it (E01.9/10)

One channel-layer group per room. A posted message is saved, then broadcast to the group, which includes the sender — so every member (and only that room's members) receives it.

# chat/consumers.py — receive_json()
await self._save_message(self.room, self.scope["user"], body)
await self.channel_layer.group_send(
    self.room.group_name,                                   # "chat.<slug>"
    {"type": "chat.message", "username": self.username, "body": body},
)
// chat/static/chat/js/chat.js — sending, and receiving for everyone
$form.on("submit", function (e){ e.preventDefault();
    socket.send(JSON.stringify({ body: $input.val().trim() })); });   // no AJAX — the socket
socket.onmessage = function (event){
    var data = JSON.parse(event.data);
    if (data.type === "message") appendMessage(data.username, data.body);
    // ... "join" / "leave" / "users" handled here too
};

Bottom, ascending, with the poster's name, never reordered (E01.11/12)

The DB orders messages oldest-first (Meta.ordering = ("created", "id")), and the client only ever appends a row — it never inserts at the top, replaces, or sorts. So the order the server sends is the order shown, permanently.

"<username> has joined the chat" — for everyone, joiner included (E01.13)

# chat/consumers.py — after accept(), broadcast to the whole group (incl. the joiner)
await self.channel_layer.group_send(
    self.room.group_name, {"type": "chat.join", "username": self.username})

Messages can't inject HTML: the client builds rows with jQuery's .text(), which escapes the content (a small but real safety point worth mentioning).

7. Exercise 02 — History

E02.1/2 A user joining sees the last three messages of that room, oldest to newest. On connect, before the join notice, the consumer replays them to that one socket:

# chat/consumers.py
@database_sync_to_async
def _recent_messages(self, room):
    limit = getattr(settings, "CHAT_HISTORY_SIZE", 3)          # 3, from settings.py
    newest_first = room.messages.select_related("user").order_by("-created", "-id")[:limit]
    return [{"username": m.user.get_username(), "body": m.body}
            for m in reversed(list(newest_first))]             # → oldest first

We fetch the newest 3 (efficient — a small LIMIT, not the whole table) and reverse them so they arrive in the right order. E02.3: they are replayed over the socket, not fetched by AJAX.

8. Exercise 03 — User list

A live list of connected users, set apart from the messages, that updates by itself; plus a "<username> has left the chat" notice.

Who is connected (E03.1/3/4/6)

Connections are tracked in a per-room dictionary, keyed by channel (not by username) so that the same person in two tabs counts correctly and closing one tab doesn't remove them:

# chat/consumers.py
_CONNECTED = {}   # {room_slug: {channel_name: username}}

def _usernames(slug):
    return sorted(set(_CONNECTED.get(slug, {}).values()))   # deduplicated, for display

Whenever someone joins or leaves, the server pushes the fresh list to the whole room — the list updates by itself, with no polling and no AJAX:

await self.channel_layer.group_send(
    self.room.group_name, {"type": "chat.users", "users": _usernames(self.slug)})

E03.2 The list is a separate container in the template (chat/templates/chat/room.html): a <aside class="users"> beside the <div id="messages">.

"<username> has left the chat" (E03.5)

# chat/consumers.py — disconnect()
if was_last:      # only when the user's last tab closes
    await self.channel_layer.group_send(
        self.room.group_name, {"type": "chat.leave", "username": self.username})

The client appends it as a notice row, after the posted messages, exactly like the join notice.

12. Questions an evaluator may ask

"Show me that login really uses AJAX and doesn't reload." → Network tab: the POST is type xhr, the response is JSON, and the Doc/navigation count never increases. Or the window.marker trick (§3).

"The chat must not use AJAX — prove it." → Network → WS shows one socket; Fetch/XHR shows nothing while chatting. All messages are WebSocket frames.

"Only jQuery is allowed." → Only jquery.min.js loads as a library; the chat uses the browser's built-in new WebSocket(...), which is not a library.

"Where are the room names stored?" → In the database, model Room (chat/models.py), seeded by a data migration. Show them in /admin/.

"Why daphne / channels?" → WebSockets need ASGI; Django alone is WSGI. daphne is the ASGI server, channels is the WebSocket framework. d09/asgi.py routes HTTP to Django and WS to the consumer.

"What happens if an anonymous user hits the socket?" → The consumer closes it with code 4401 (chat/consumers.py), and the pages are @login_required.

"Why is the history exactly 3 and in that order?" → CHAT_HISTORY_SIZE = 3 in settings.py; we take the newest 3 by -created then reverse to oldest-first (§7).

"Where are your credentials?" → In .env, git-ignored; settings read it and refuse to start without it. Only .env.example (placeholders) is committed (G10).
